# R8 REDUNDANT Profile 3 v0.1

> Status: normative Gate-0 contract for private, experimental, closed-lab R8 only.

## 1. Profile and admission

Profile 3 is authenticated two-path endpoint delivery. It does not establish physical separation and makes no inference about topology beyond recorded experiment evidence. A Profile-3 session starts with one validated path in slot zero using `0005-session-security-v0.1.md` and the outer packet rules in `0004-wire-format-v0.2.md`. Slot one is unavailable until it completes the exact candidate procedure in `0006-mobility-v0.1.md`.

The sole slot-one admission sequence is: protected signed `LOC_UPDATE` proposal sent on validated slot zero; candidate-originated protected `BIND_PROBE`; receiver-observed typed `UdpBinding` or `NativeBinding`; challenge token bound to identity, SCID, Profile 3 policy, candidate ID, LOC, epoch, direction, and slot one; exact-binding protected response before challenge expiry; then promotion. Configuration and passive receipt are not admission evidence. A candidate failure cannot remove slot zero or change either replay state.
Every admission control is plaintext inside an authenticated Profile-3 `SESSION_DATA` packet and enters the candidate manager only through the redundant session's transactional receive preview. That exact preview is the replay-commit capability: candidate validation succeeds first, then session replay/delivery state and mobility state commit as one serialized operation. At most `P-REDUNDANT-RECEIVE-PREVIEWS-MAX` may be outstanding. A caller-fabricated replay token, direct raw-control injection, or a manager without the exact session callback is invalid. `BIND_PROBE` may be transported with the active slot-zero key on the candidate carrier; successful AEAD alone grants no candidate binding or slot-one authority.

There are exactly two path slots, `0` and `1`. A removed slot is permanently unavailable until a fresh session; it is never reused. Each validated slot has a distinct HKDF key derived using Profile 3 and its path slot as specified in `0005-session-security-v0.1.md`, a distinct send counter, and a distinct receive replay window. All counter, nonce, AEAD, atomic reservation, exhaustion, restart, and replay requirements in that document apply independently to each slot. There is no key reuse between slots.

## 2. Canonical Profile-3 data encoding

A Profile-3 `SESSION_DATA` (SES type 6) payload uses the common four-byte SES prefix and then exactly:

```
counter:u64 || delivery_id:u64 || ciphertext_and_tag:variable
```

The plaintext is the application bytes. The `delivery_id` is a `u64` in exactly the registry's `P-DELIVERY-ID` usable range, is generated once per logical outbound delivery, and is outside ciphertext but authenticated. AEAD associated data is the canonical 48-byte header defined in `0005-session-security-v0.1.md`, the SES four-byte prefix, `counter:u64`, and `delivery_id:u64`, in that order. The nonce remains `0x00000000 || counter_u64_be` under the key for that slot. A packet is valid only when header Profile is exactly 3, header Path Slot equals the key/replay slot used, and body layout is exact. Profile-3 `CLOSE` is SES type 7 and retains the common protected `counter:u64 || ciphertext_and_tag:18` layout; it has no delivery ID.

A logical delivery is serialized once per active slot with the same `delivery_id` and identical application bytes, but with its own slot key/counter/nonce and outer header binding. A sender must not use an identical delivery ID with different application bytes. Binding budget computation uses the registry formula and subtracts base header, SES prefix, two `u64` fields, tag, and any selected carrier metadata. Oversize application data fails before any slot counter reservation and is never fragmented.

Delivery IDs atomically increase with no wrap and use `P-DELIVERY-FORWARD-GAP-MAX`. Allocation starts at a random nonzero value after handshake. Before delivery-ID exhaustion, the sender closes and releases the session; it does not reset the sequence or create a replacement key.
The receiver's delivery high-water mark is unset at session establishment. The first successfully authenticated Profile-3 `SESSION_DATA` delivery ID anchors it to that ID without a forward-gap comparison. Thereafter, only an ID greater than the high-water mark is a forward delivery, and it is eligible only when `delivery_id - high_water_mark <= P-DELIVERY-FORWARD-GAP-MAX`; accepting such an ID advances the high-water mark. An ID at or below the high-water mark is evaluated only by the identity-window rules and never lowers the mark.

## 3. Path and delivery state contract

Session delivery state contains a delivery high-water mark, an authoritative `P-DELIVERY-IDENTITY-WINDOW` mapping each retained delivery ID to its SHA-256 digest and byte length, and a separate `P-DEDUP-CACHE-IDS` full-plaintext cache. A plaintext cache entry expires after `P-DEDUP-CACHE-EXPIRY`; expiry erases only plaintext, never an identity still inside the window. The identity window is retained until session release or until its fixed numeric capacity advances past an older ID; such an older ID fails closed. Each active path has one bounded queue. Limits and overflow policy are exactly `spec/parameters-v0.1.md`: each queue is limited to the registry packet and byte bounds; overflow drops the newest packet with telemetry.

A receiver applies the delivery high-water-mark rule after successful AEAD and before identity-window insertion; an invalid forward ID or an ID older than the window does not mutate delivery state and fails closed. The first successfully authenticated Profile-3 `SESSION_DATA` delivery ID anchors the high-water mark without a forward-gap comparison. The identity window stores a SHA-256 digest and byte length sufficient to distinguish every accepted payload while its ID remains in the bounded window; it must never treat unequal bytes as equal. The full plaintext cache is optional only after its `P-DEDUP-CACHE-EXPIRY` expiry; identity-window comparison remains authoritative until numeric window advancement evicts that ID. Equal delayed copies suppress after plaintext expiry while their ID remains; a divergent delayed copy closes the session; an older evicted ID fails closed without redelivery. Divergence is detected only after each candidate packet has separately passed the corresponding path's AEAD and replay checks.
With two active slots, outbound preflight is global and all-or-none: before allocating a delivery ID or reserving either counter, the sender checks both serialized-path budgets, both per-path queue limits, and both usable counters. If either path fails any check or is full, it drops the newest logical delivery, consumes no delivery ID or counter, and enqueues neither copy. Each per-path queue retains its own registry packet and byte limits; global preflight does not alter those limits.

## 4. Degradation and errors

With both slots active, each logical delivery is sent over both. With exactly one active slot, the session remains protected but is `DEGRADED`; it emits one bounded degraded event on transition and one recovered event only when a newly admitted slot becomes active. Degraded intervals must be labeled as single-path in measurement output. No silent switch to an unprotected carrier or unauthenticated path is permitted.

Internal reason tags are externally reported only as registry categories: candidate/admission failure is `E-CANDIDATE`; queue/dedup/divergence/path authorization failure is `E-PATH`; capacity is `E-CAPACITY`; replay is `E-REPLAY`; counter exhaustion is `E-COUNTER`; and budget failure is `E-BUDGET`. Telemetry is bounded by these categories plus queue/window high-water marks, dedup suppression, divergence, and degradation/recovery transitions. It contains no application bytes, keys, cookies, tokens, raw pins, EIDs, SCIDs, LOCs, IPs, or MACs.
